# Generic Rules

**Mandatory** — applies to every AI coding assistant (Cursor, Claude Code, and similar) working in any repository of the workspace. Injected into Cursor sessions via the thin stub at `.cursor/rules/`. The project layers add their own rules on top: `kapita/.ai-config/rules/kapita-rules.md` (product) and `shipdeck/.ai-config/rules/shipdeck-rules.md` (tools and platform). Numbering is kept from the original single rules file, so older references to "rule 12" or "rule 21" still resolve here.

## Operating Rules

1. **Analysis check**: Ensure understanding of the task.
2. **No speculation**: Inspect the repository and relevant files before making claims.
3. **Specification check**: Align with requirements and business needs (the project's product skills, indexed by its skills index).
4. **Code change**: Respond to specifications and technical/functional requirements.
5. **Minimal diffs**: Keep changes focused, avoid unrelated refactors.
6. **System design check**: Respect architecture and design patterns (`.ai-config/skills/architecture.md`).
7. **Design system check**: For frontend changes, respect design system (`.ai-config/skills/design-system.md`); use `react-design.md` for component design and `figma-design.md` for design/Figma work.
8. **Tests included**: Add or update tests as applicable (`.ai-config/skills/testing.md`). **Unit tests** cover configuration, driver, and driven code only; **mirror `src`** under `tests/unit/` (e.g. `tests/unit/driven/spi/user/test_user_repository.py`). **Use case tests** invoke use case classes with mocked ports—**do not** add domain unit tests or “move” domain tests into the use-case folder as a substitute. Add **extra use case tests** for corner cases when raising domain coverage; **do not** reach for domain **service** unit tests for those corners. **New web contexts:** scaffold `vitest.config.mts` and `test/support/test-router.tsx` (when testing routed UI) per `testing.md` § *Web frontend Vitest conventions*—never `vitest.config.ts` or raw `MemoryRouter`/`BrowserRouter` in tests.
9. **Observability**: Propagate identity and debug context across clients and BFF (`.ai-config/skills/observability.md`); structured logs at boundaries; no PII in telemetry.
10. **Evidence captured**: Use Evidence Template (`.ai-config/skills/evidence.md`).
11. **Fail-safe**: If constraints cannot be met, stop and ask for guidance.
12. **Commit**: Before committing, ensure all evidence is checked. Use **Conventional Commits** with a domain scope: `type(domain/context)/area: imperative summary` (`area` is one of the project's areas; Kapita: `backend` | `web` | `mobile` | `testing` | `docs` | `cursor`); blank line, then a **body** with description. Full spec and examples: `.ai-config/hooks/session-context.md` (Commit messages) and `.ai-config/skills/evidence.md`. One small atomic commit per repository and per step; never push without being asked.
13. **Robot E2E vocabulary**: Functional Robot suites under `testing/e2e/backend/` use **business-domain language** in test-case titles, `[Documentation]`, and keywords invoked from test cases (no URLs, HTTP codes, or wire-format jargon there). Technical calls belong in `libraries/ApiLibrary.py` and resource keyword bodies. See the Robot Framework E2E section in `.ai-config/skills/testing.md`.
14. **Frontend decomposition**: For web (`frontend-web`) and mobile (`frontend-mobile`), preserve refactor discipline by favoring smaller composable components/widgets, extracting reusable logic to hooks/helpers/use-cases, and keeping clear container-vs-presentational boundaries.
15. **Frontend atomic hexagonal placement**: Feature objects/views/pages stay inside their owning domain or capability context (`presentation/featured`, `presentation/components`, `presentation/pages`, etc.). Generic atomic UI belongs in `frontend-web/packages/core/lib/core-ui` or `frontend-mobile/packages/core/lib/core-ui` as atoms/molecules/organisms/templates with token-based styles and tests. `frontend-mobile/apps/app-mobile` is routing/composition only (thin screen re-exports)—see `docs/architecture/1.atomic-hexagonal-architecture.md` § Frontend mobile — app shell and placement. When a page/component grows too large or becomes reusable, split it before adding more behavior.
16. **Agent shell (non-interactive)**: When the agent runs shell copies on macOS, use `/bin/cp -f` (not `cp -f`) to avoid `cp -i` overwrite prompts; agent terminals cannot accept interactive `y/n` input. See `.ai-config/skills/shell.md`.
17. **Backend lint before finish**: After backend Python changes (`src/`, tests, or `scripts/`), run package lint and fix all ruff/mypy errors before ending the turn or committing. Composer hooks track touched packages; see `.ai-config/skills/backend.md` § Lint before finishing.
18. **Web lint before finish**: After frontend-web changes (`.ts`, `.tsx`, `.css`, tests), run `make -C frontend-web lint-package PACKAGE=…`, fix eslint errors, run `type-check` when TS changed, and verify app build when Tailwind `@apply` CSS changed. See `.ai-config/skills/web.md` § Lint before finishing.
19. **Mobile lint before finish**: After frontend-mobile Dart changes, run `make -C frontend-mobile lint-package PACKAGE=…` and fix all `flutter analyze` issues before ending the turn or committing. See `.ai-config/skills/mobile.md` § Lint before finishing.
20. **Python-first scripts**: New repo utilities under `scripts/` should be Python (`python3 scripts/<domain>/<tool>/<tool>.py`, with a `README.md` in the tool folder) with tests in `scripts/tests/` when logic is non-trivial. Shell is acceptable only for thin Makefile glue, required executable hooks, or documented legacy helpers. See `.ai-config/skills/scripts.md`.
21. **Build-time generated files are never committed**: Anything a build step generates or copies from a monorepo original is a *transient build material* — produced during the build, baked into the image, and not needed afterwards. Untrack it (`git rm --cached`) and add it to `.gitignore`; never commit the refreshed copy; edit the original, never the copy. **Distinguish this from committed generated artifacts** — files a manual `make` target produces that are *inputs* to a build (for example an architecture map JSON or a releases timeline). Those stay tracked because the build copies them in rather than producing them, and CI guards their freshness with a `--check` mode. The test is whether the build produces the file or consumes it. See `.ai-config/skills/scripts.md`; the documentation bundle is the reference case (`shipdeck/.ai-config/skills/shipdeck-documentation-tube-skills.md`).
22. **Infrastructure and cluster as code**: The infrastructure and the cluster must be rebuildable from the repositories alone, so the whole stack can be recreated and redeployed quickly (for example when changing provider). Every change to a server or to the cluster is made in code first and committed: node setup in the configuration-management repository (playbooks and variables, with the real inventory derived from an example), everything that runs in the cluster in the GitOps repository (applications, chart values, resources, sealed secrets) and the Helm charts. A GitOps controller with `selfHeal` reverts a live `kubectl` edit; change git, not the cluster. A manual change is allowed only as an emergency or a one-off and must be reproduced in code in the same session, with the playbook made idempotent. Never leave a setting that exists only on a machine; prefer provider-agnostic code and keep the rebuild runbook current. See `.ai-config/skills/kubernetes-cluster.md`; the concrete layout is in `shipdeck/.ai-config/rules/shipdeck-rules.md` (rule 5) and `shipdeck-infra-skills.md`.
